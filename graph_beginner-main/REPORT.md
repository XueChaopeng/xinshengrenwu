## 0. 摘要

本实验用 **PyTorch Geometric (PyG)** 完成了 README 要求的四个任务：

| 任务 | 内容 | 数据集 | 模型 |
|---|---|---|---|
| 一 | 节点分类 | Cora / Citeseer / Flickr | GCN / GAT / GraphSAGE / GIN |
| 二 | 链路预测 | Cora / Citeseer / Flickr | GCN / GAT / GraphSAGE / GIN |
| 三 | 图分类 / 图回归 | MUTAG / ENZYMES / PROTEINS / IMDB-BINARY / ZINC | GCN / GAT / GraphSAGE / GIN，四种池化 |
| 四 | 知识图谱补全 | WN18RR / FB15k-237 | TransE / RotatE / ConvE |

主要结论（详见各章）：

1. **采样子图训练在精度上普遍不劣于全图**：节点分类 12 组对比中 11 组、
   链路预测 12 组中 8 组，采样达到或超过全图。Flickr 节点分类上，
   采样在**全部四个模型**上都超过了全图。
2. **速度优势并不普遍，而且很容易测错**。采样只有在「大图 + 高开销聚合」时
   才明显更快（Flickr + GIN 达 1.94×）；中小图上因为采样与子图组装的固定开销，
   采样反而更慢（0.52×–0.80×）。更重要的是：**第一次测量时后台还有其它 CUDA
   任务，把 Flickr GCN 全图的墙钟时间从 46.5 秒记成了 213 秒**，
   一度得出「采样快 1.95×」的错误结论。这类对比必须在 GPU 独占下进行
   （见 2.5 与 6.11）。
3. **学习率是影响最大的超参数**，且全图与采样两种模式的最优学习率不同
   （小 batch 的梯度噪声更大，需要更小的步长）。
4. **采样器的 fanout 必须与图的平均度匹配**：Flickr 平均度 20，用 `[10,10]`
   的子图比整张图还大，反而比 `[5,5]` 更差。
5. **GAT 在大图上训练困难**：Flickr 上全图 GAT 在节点分类（42.34%）和链路预测
   （60.37 AUC）两个任务上都明显落后于其它模型，而采样训练能显著改善
   （50.16% / 65.71）。
6. **知识图谱补全的模型排名符合理论预期**：RotatE (MRR 0.387) ≫ TransE (0.201)
   ≫ ConvE (0.058)。RotatE 的旋转几何能建模对称与逆关系，而 WN18RR 正是以
   这两类关系为主；TransE 的平移几何在原理上无法表示对称关系。

## 1. 环境与通用方法

### 1.1 硬件与软件

| 项目 | 配置 |
|---|---|
| 操作系统 | Windows 11 |
| Python | 3.13.11 |
| PyTorch | 2.7.1+cu118 |
| PyTorch Geometric | 2.8.0 |
| PyG 采样扩展 | pyg-lib 0.4.0 / torch-sparse 0.6.18 / torch-scatter 2.1.2 / torch-cluster 1.6.3 |
| GPU | 单张 NVIDIA GPU（CUDA 可用） |

### 1.2 框架选择：为什么选 PyG 而不是 DGL

README 允许在 DGL 与 PyG 之间二选一。本实验选择 **PyG**，原因有两点：

1. **环境兼容性**：实验机是 Python 3.13，DGL 尚未提供该版本的官方 wheel，
   而 PyG 2.8 + `pyg-lib` 已完整支持。
2. **采样器**：作业要求「利用框架自带的 Sampler 采样子图进行训练」，
   PyG 提供 `NeighborLoader`（节点级）与 `LinkNeighborLoader`（边级），
   正是任务一、二需要的能力。

> 附注：README 参考链接给出的 DGL 邻居采样教程
> （`L0_neighbor_sampling_overview`）在概念上与 PyG 的 `NeighborLoader` 完全对应：
> 都是以一批种子节点为中心、按每跳 fanout 采样固定数量的邻居，
> 再在诱导出的子图上做消息传递。

### 1.3 通用实验设置

- **随机种子**：核心对比实验（任务一、二的 `main` 组）用 3 个种子（0/1/2），
  报告均值 ± 标准差；超参扫描用 1–2 个种子以控制总时长。每个配置实际使用的
  种子数可从 `results/detail/*.json` 核对。
- **模型选择**：一律按**验证集**指标早停，保存验证集最优权重，最后在测试集评测。
  测试集从不参与调参或早停。
- **计时方式**：`utils.Timer` 在计时前后都调用 `torch.cuda.synchronize()`，
  测到的是真实墙钟时间而非异步 kernel 的排队时间；计时包含每轮的验证评估
  （两种训练模式一致，保证可比）。
- **结构公平性**：同一任务内四个模型共享同一个 `GNNEncoder` 骨架
  （只替换消息传递层），层数、隐藏维度、dropout、优化器完全相同。

### 1.4 数据集获取：网络限制与镜像

实验所在网络**无法访问 Google Drive、Dropbox 与 huggingface.co**，
而多个数据集的官方源恰好位于这些站点。解决方式如下（脚本均已内置，可复现）：

| 数据集 | 官方源 | 实际使用的镜像 |
|---|---|---|
| Cora / Citeseer | `github.com/kimiyoung/planetoid` | 可达，直接使用 |
| **Flickr** | Google Drive（PyG 2.x） | **`https://data.dgl.ai/dataset/flickr.zip`**（DGL 公开镜像，GraphSAINT 原版四文件） |
| TUDataset | `chrsmrrs.com` | 可达，直接使用 |
| **ZINC** | Dropbox（PyG） | **`https://hf-mirror.com/datasets/graphs-datasets/ZINC`**（标准 PyG 划分的 jsonl） |
| WN18RR / FB15k-237 | `raw.githubusercontent.com` | 可达（需重试），直接使用 |

所有数据都下载到各任务自己的 `data/` 目录（E 盘），不写入 C 盘用户目录。

## 6. 实现过程中发现并修复的问题

这一节记录调试过程中**实际定位并修复**的缺陷。它们对结果的量级有决定性影响，
因此单独列出以说明结果的可靠性，也说明为什么某些章节的数据是重跑后才可信的。

### 6.1 任务一：采样跳数与网络层数不匹配（影响最大）

**症状**：Flickr 上 GCN 的采样训练只有 **43.9%**，而全图训练有 49.5%；
且采样模式的最佳 epoch 出现在第 1 轮。

**根因**：`resolve_fanout()` 把采样跳数写成了 `num_layers - 1`。
但 `L` 层消息传递需要 **`L` 跳**邻居：第 1 层消费 1 跳邻域，第 2 层消费的是
1 跳节点已经聚合过的 2 跳邻域……少采一跳会让**最外层卷积收不到有效信息**。

**修复与效果**：改为 `hops = num_layers` 后，Flickr 上采样训练的准确率
从 43.9% 提升到 **50.4%**（GCN），反超全图训练。

### 6.2 任务一：学习率在两种训练模式下的最优值不同

**症状**：统一用 `lr=0.01` 时，采样训练在 Flickr 上明显劣于全图。

**根因**：mini-batch 梯度是整图梯度的**有噪估计**，噪声随 batch 减小而增大，
沿用全图学习率会导致优化在最优解附近震荡。

**修复与效果**：采样模式单独设置更小的学习率（Flickr 用 0.003，全图仍用 0.01）。
GraphSAGE 的采样结果从 43.9% 提升到 **51.2%**。
本报告由此把「学习率」列为影响最大的超参数。

### 6.3 任务四：head 侧排名的查询起点写反了

**症状**：RotatE 在 WN18RR 上 MRR ≈ 0.0002（相当于随机），TransE 也只有 0.125；
但训练损失能正常下降——**训练目标在优化，评测指标却不动**。

**定位过程**：写了一个小规模过拟合测试（几百个三元组训练上千步），
发现 loss 降到 0.164 而 train MRR 只有 0.46。这说明**训练用的打分函数和
评测用的打分函数算的不是同一个东西**。进一步逐元素对比：

```
score(h, r, t)          与  score_all_tails(h, r)[t]   完全一致 (diff = 0)
score(t, r_inv, h)      与  score_all_heads(r, t)[h]   差了 3.09   ← 问题在这
```

**根因**：`score_all_heads` 的语义是「对 `(?, r, t)` 给**所有候选头**打分」，
因此查询必须从 **tail** 出发（`(t, r⁻¹, ?)` 才是 `(?, r, t)` 的镜像）。
原实现把 **head** 当成了查询起点，等于在给完全无关的候选打分。
filtered MRR 是 head 侧与 tail 侧排名的平均，所以 head 侧全错会把 MRR 直接腰斩。

**修复与效果**：改为 `score_all_tails(tail, inv)` 后，
train MRR 从 0.4575 升到 **0.8906**，验证集 MRR 提升 **76%**。
TransE 的 0.125 也出自同一个缺陷。三个模型（TransE / RotatE / ConvE）
都有这个函数，已一并修复，并用逐元素对比验证了修复的正确性。

### 6.4 任务四：RotatE 的 margin 被错误地乘进了嵌入

**症状**：RotatE 完全学不动。

**根因**：模型内部计算 `h * gamma` 再旋转。但**旋转是保模长的**
（`|r_i| = 1`），把 `h` 放大 `gamma` 倍会破坏整个几何结构。
官方实现中 `gamma` 只是**加性**的 margin：`score = gamma - ||h ∘ r - t||`。

**修复**：移除模型内部的 `gamma` 缩放，只让它在损失函数里作为 margin 出现。

### 6.5 任务三：ZINC 的实验结果从未写进 CSV

**症状**：`all_results.csv` 里一个 ZINC 行都没有，但 `detail/` 下 ZINC 的
JSON 文件却是齐全的——**训练明明跑完了**。

**根因**：`_csv_row()` 里用 `stats["num_graphs"]` 兜底训练集规模，
而 TUDataset 的统计里有 `num_graphs`，ZINC 的统计里只有
`count` 和 `splits`。于是 ZINC 每次训练完都在写 CSV 时抛 `KeyError`，
异常被批量运行器的 `try/except` 吞掉，只留下一行没人注意的错误输出。

**修复**：新增 `_split_sizes()`，对两种数据集分别取正确的字段
（TUDataset 用 `num_graphs` 的 80%，ZINC 用固定的 `splits`），
并用两种数据集各跑一次验证了写入正常。

### 6.6 任务一：`resolved()` 的默认值判定会静默吞掉显式参数

**症状**：`--batch-size 64` 在 Flickr 上被悄悄改成了 1024。

**根因**：原实现用「参数值是否等于全局默认值」判断用户有没有显式传参。
`Config.batch_size` 的全局默认恰好也是 64，于是在 Flickr 上被判为
「未指定」而被数据集默认值覆盖。

**修复**：把可调参数的类型改成 `Optional`，用 `None` 作为「未指定」的哨兵。

### 6.7 采样负样本的性能陷阱（任务二）

`torch_geometric.utils.negative_sampling` 在 Cora 上每次调用要 **20.8 ms**，
而等价的 GPU 均匀采样只要 **0.6 ms**——相差 **35 倍**，因为它会在 CPU/GPU
之间往返。对这三个稀疏图而言，均匀采样撞到真实边的概率可以忽略
（Cora 0.14%、Flickr 0.011%），因此默认切换到 GPU 版本，
并保留 `--neg-sampler pyg` 供需要严格过滤的场合使用。

### 6.8 任务四：排名计算的 off-by-one，使 Hits@1 恒为 0

**症状**：TransE / RotatE / ConvE 三个模型的 **Hits@1 全部是 0.0**，
而 Hits@3 却有 30% —— 这在统计上几乎不可能，说明指标本身有问题。

**根因**：`_rank_of()` 里

```python
greater = (scores > target_score).sum(dim=1)
equal   = (scores == target_score).sum(dim=1)   # 包含目标自己，因此 equal >= 1
return (greater + (equal + 1) // 2 + 1).long()  # ← 末尾多了一个 +1
```

正确答案排在第一位时 `greater = 0, equal = 1`，按乐观约定应当得到 rank **1**，
而该式给出 `0 + 1 + 1 = 2`。**所有排名被整体后移一位**，
于是 Hits@1 恒为 0，MRR 也被系统性低估（算的是 `1/(r+1)` 而不是 `1/r`）。

**修复与验证**：去掉多余的 `+1`，并补了单元测试：
唯一最优 → rank 1；并列最优 → rank 1（乐观约定）；最差 → rank 3；
**完美排序器的 MRR = 1.0**。

### 6.9 任务三：`--reset` 与断点续跑的先后顺序颠倒

**症状**：加了 `--reset` 重跑后，MUTAG / ENZYMES / PROTEINS / IMDB-BINARY 的
`main` 结果**全部消失**，而 CSV 里只剩 ZINC 的行。

**根因**：`run_experiments.py` 原先按 `resume 扫描 → reset 删除` 的顺序执行。
扫描读到的是**即将被删掉的**旧 CSV，于是把所有已完成的配置都判定为
「无需重跑」并从计划里剔除；紧接着 `--reset` 把那些结果删掉。
净效果就是「删了结果，又什么都没重跑」。

**修复**：把 `--reset` 提到 resume 扫描之前，并在 reset 之后强制关闭 resume。

### 6.10 任务四：RotatE 的实体初始化尺度错了 70 倍（影响最大）

**症状**：在 6.8 的排名 bug 修好之后，TransE 恢复到 MRR 0.137，
**RotatE 却仍然停在 0.0024**（约等于随机）。而且诊断时出现一个反常现象：
把负样本数从 64 提到 256，结果**一模一样**（val MRR 都是 0.0018）——
这说明模型几乎没在学，输出基本由初始化决定。

**根因**：实体嵌入的初始化范围写成了 `uniform_(-1, 1)`，但 RotatE 的
官方实现是

```python
embedding_range = (gamma + epsilon) / dim        # epsilon = 2.0
entity = uniform_(-embedding_range, embedding_range)
```

以 `dim=500, gamma=5` 计，官方范围是 **±0.014**，初始时 `||h ∘ r − t||₁ ≈ 2`，
与 margin（gamma=5）处于同一量级。而 `±1` 让初始距离变成约 **134**，
margin 却还是 6 —— **两者相差 20 倍以上**，排序损失的信号被彻底淹没。

**修复与效果**：按官方公式初始化后，RotatE 在 WN18RR 上
**只训练 20 个 epoch（2 分 46 秒）就达到 MRR 0.386**，
相比修复前的 0.0024 提升约 **160 倍**，Hits@1 从 0 升到 37.5%。

**顺带修正的一个结论**：代码里原本注释说「RotatE 在 lr=1e-3 下会崩溃，
所以要用 1e-4」。初始化修好之后实测恰恰相反 —— 1e-3 明显优于 1e-4。
**那个「崩溃」的真正原因是初始化尺度，不是学习率**，
原先的注释把因果搞反了。这也说明：当两个超参数同时可疑时，
先隔离出真正起作用的那一个再调另一个。

### 6.11 测量方法本身出过错：并发 CUDA 任务污染墙钟时间

这一条不是代码 bug，而是**实验方法上的失误**，而且它一度让报告得出了相反的结论，
因此单独记录。

**症状**：第一轮主实验给出的时间是

| 配置 | 第一轮 | 干净重跑 |
|---|---|---|
| Flickr / GCN / 全图 | 213.4 s | **46.5 s** |
| Flickr / GCN / 采样 | 109.4 s | **46.0 s** |
| Cora / GAT / 全图 | 4.63 s | **1.79 s** |

第一轮据此得出「Flickr 上采样比全图快 **1.95 倍**」，
而干净重跑显示两者**基本持平（1.01×）**。

**根因**：第一轮运行时后台还有别的 CUDA 任务（本项目的其它实验、以及调试用的
脚本）在抢同一张 GPU。GPU 时间被两个进程分时复用，
谁的墙钟时间都会被拉长，而且**拉长的幅度取决于另一方的负载波动**，
因此这个误差**不能靠多次取平均消除**。

**处理**：
1. 把主实验在 GPU 独占的条件下**完整重跑**一遍，结果写入
   `results/timing/`，报告中的速度对比一律采用这一份数据；
2. 后续所有实验改为**严格串行**执行；
3. 在 `README.md` 的复现步骤里明确写出这个前提。

**教训**：作业要求「对比全图训练和分批次训练的运行时间」，
这类对比的前提是**独占硬件**。精度指标对并发是鲁棒的（本项目的准确率在两轮之间
几乎完全一致，例如 Cora GAT 全图两轮都是 79.97%），
但墙钟时间不是——同一份代码可以给出「快 2 倍」和「一样快」两个结论。

## 7. 复现指南

每个任务都可独立运行，命令见各自的 `README.md`。完整流程：

```bash
pip install -r requirements.txt
pip install pyg-lib torch-sparse torch-scatter torch-cluster \
    -f https://data.pyg.org/whl/torch-2.7.1+cu118.html

for t in task1_node_classification task2_link_prediction \
         task3_graph_classification task4_knowledge_graph; do
    (cd $t/code && python prepare_data.py)
done

(cd task1_node_classification/code && python run_experiments.py --experiments main --reset && python summarize.py)
(cd task2_link_prediction/code     && python run_experiments.py --experiments main --reset)
(cd task3_graph_classification/code && python run_experiments.py --experiments main pooling --seeds 0 1 --reset)
(cd task4_knowledge_graph/code     && python run_experiments.py --experiments main --datasets WN18RR --seeds 0 --reset)
```

> ⚠️ **关于计时数据**：作业要求对比「全图训练与分批次训练」的**运行时间**。
> 请确保同一时刻只有一个 GPU 任务在跑——两个 CUDA 进程并行会让墙钟时间失去意义。
> 本报告的计时数据是在串行执行下测得的。
